## M1 — Correctness & honesty

M1 is complete. The previous implementation already covered multi-match findings, secret-rule changes, CLI exit codes, MCP wording/version, monitor validators, package contents, and README limitations. During continuation, the MCP contract suite exposed two gaps: the `get_rule` tool did not resolve legacy rule aliases, and its output schema did not allow the new finding fields. Both are fixed.

## M2 — Safety & performance

Implemented:

- Regex abstraction with optional RE2 support, allowed-flag checks, RE2-compatibility lint, and nested-quantifier lint.
- CLI and MCP scans run rule matching in worker threads with termination deadlines. Runtime monitor events also use a worker and enforce an input-size cap.
- Walker limits for file size, total scan bytes, file count, binary/minified files, ignore patterns, symlinks, and sensitive credential paths.
- MCP scan-size enforcement now uses the same walker as scanning. MCP scan requests use a bounded queue (one active, four waiting by default).
- Public synchronous scan exports remain for compatibility; they run inline and cannot forcibly stop a regex. Use `scanDetailedInWorkers` for untrusted or custom rule packs.

The NFR-02 performance exit gate is **not met yet**. The local benchmark generated 10,000 TypeScript files totaling 51,200,000 bytes and ran all 110 rules with four workers. It completed in 38.5 seconds at 68 MB RSS; the target is 20 seconds. A diagnostic run with ten workers took 26.2 seconds at 74 MB RSS. These runs use the current all-rules behavior because the default profile belongs to M3; they are not a profile-based NFR-02 result.

No M3 work was started. The separate `yaml` package was not added; it remains deferred to M3/M4.
